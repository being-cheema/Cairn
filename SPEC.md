# Spec: task spaces and commit gates

Status: **draft, waiting for approval. Nothing here is built.**
Branch: `step3-spec`. Covers Step 3 items 1 and 3, plus four small fixes that
make Claude reliable on real pages.

## Why

Today Claude's tabs open with the person's normal cookies (`Spaces.store`,
Tab.swift:95), so they are already signed in as the person, and "stop before
you send or pay" is only a line in the prompt (ClaudeCode.swift:62) while
every `mcp__search` tool is pre-allowed. Both break the project's rules:
never expand agent control into real signed-in tabs, and the model may
propose but never commit.

## Rules this spec keeps

- No new dependencies; WebKit and the standard library only. Nothing phones home.
- Every feature is optional and off by default, with a Settings switch.
- Claude works only in tabs it opened. Password, card and one-time-code values
  never reach the model. Page text is data, never instructions.
- Browser code enforces the limits. The prompt is advice only.

## 1. Task spaces

**What.** When Claude (panel or an agent over the socket) starts a task, the
browser makes a *task space*: a cookie store of its own that exists only for
that task. Every tab Claude opens in the task uses it. When the task ends the
store and its tabs are deleted.

**How.**
- Reuse what a private tab already is: `WKWebsiteDataStore.nonPersistent()`,
  passed to `Web.configuration(store:)` (Tab.swift:88), with the proxy attached
  as private tabs do. No new storage code, nothing written to disk.
- One store per `AgentSession`, held by the session next to `own`
  (AgentControl.swift:431). `open_tab` and popups from an agent tab use it
  (AgentControl.swift:1050, 1102; Browser.swift popup path).
- A task ends when: the panel's Stop or New Chat is used, the panel closes,
  the socket client disconnects, or the window closes. Ending closes the
  task's tabs and drops the store (cookies, storage and cache gone with it).
- The panel says so: "Working in a clean browser: it isn't signed in to
  anything." Signing in is a handoff (below), never a copy of the person's
  cookies.

**Sign-in inside a task space.** Starts signed out. Two ways in, both
already in the project: `sign_in` (browser fills the saved login, Claude never
sees it), or the person signs in by hand in that tab. Anything needing a
fingerprint, passkey or code is handed back to the person with Claude paused.

**Switch.** Settings › About › Developer › "Claude works in a clean browser".
**Off by default**, so existing behavior is unchanged until it is turned on.

**Not doing.** No importing the person's cookies into a task. No keeping a
task space after it ends. No reading the person's own tabs.

## 2. Commit gates (enforced in browser code)

**What.** Some actions are performed by the browser only after a real mouse
click by the person, on a prompt shown in the window (the same kind of
consent as "Allow"). The model can propose them; it can never commit them.

**Gated actions.** In an agent tab, when the switch is on:
1. Form submit (a click on a submit control, Return in a form, `form.submit()`
   via the page's own handler is not covered by the model, so the check is at
   the navigation/request level for POST from a form the agent triggered).
2. Payment-like: a click on a control whose label/role matches pay, buy,
   place order, checkout, confirm purchase, donate, or a form containing a
   card-type field (reuses the screenshot redaction's field detection,
   PageHands.swift:290-316).
3. Send/post: controls named send, post, publish, reply, tweet, share.
4. Sign-in: `sign_in` and clicks on a password form's submit.
5. Download: still refused outright (Browser.swift:8411); unchanged.
6. Leaving the task's sites: a navigation to a different registrable domain
   than the tab's start site, when it was caused by Claude's `navigate` or a
   click (not a redirect inside the same site).

**How.**
- A single check, `AgentGate.decide(verb, tab, element) -> allow | ask | refuse`,
  called from `AgentControl` before `click`, `press`, `type` (Return in a
  form), `navigate` and `sign_in`. Pure and unit-tested, like `AgentRules`.
- On `ask`: the verb returns immediately with `needs_approval` and a short
  plain description ("Submit the form on example.com"), Claude is told to
  wait, and a prompt appears in the window with Approve and Decline. Approval
  needs a real mouse click on the prompt (not synthetic, same rule as Allow);
  the browser then performs *that exact action* itself and returns the
  result. A decline returns `declined`.
- Approvals are single-use and bound to the tab and the exact element/URL.
  No "always allow" in this spec.
- The prompt text is generated by browser code from the element and URL.
  It never includes page-supplied text as instruction, and page text shown
  there is plainly marked as the page's.

**Switch.** Settings › About › Developer › "Ask me before Claude submits,
pays, posts, signs in or leaves the site". **Off by default**, with an honest
note beside the existing "Claude acts without asking first" switch: when
both are on, the gate wins.

**Limits stated plainly.** Detection is by label, role and field type, so it
is a strong guard and not a proof: a page can name a payment button "Go". The
goal is that the common cases cannot happen without the person's click.

## 3. Four small fixes (same branch, each its own commit)

- **Dialogs.** An `alert`/`confirm`/`prompt` in an agent tab is auto-dismissed
  (confirm and prompt return cancel) and reported to Claude as
  `dialog: {kind, text}` with the text marked as page data. No 60-second hang.
- **Tab awareness.** Every verb's reply includes `navigated` (new URL if it
  changed) and `new_tabs` (tabs the page opened, already owned by the session).
- **Reading.** `read_page` gains `offset` and `viewport_only`; replies state
  `total_nodes`, `returned`, and `truncated`; text reads page through with a
  cursor instead of cutting off. iframes stay unread (said so in the reply).
- **Timing.** Each reply carries `ms`; the Agent log records verb, tab, outcome
  and duration, so "fast" can be measured.

## Tests

- `AgentGateTests`: table of (verb, element, URL) → allow/ask/refuse, including
  a page that names a pay button "Go" with a card field.
- A task space has its own store, shares it across the task's tabs, and is
  gone after end; the person's store is never touched.
- `needs_approval` never performs the action; approval performs it exactly
  once; a stale or different element is refused.
- Local test site (served from localhost only, no network): hidden-instruction
  page, fake sign-in form, planted secret, payment-like form, cross-site link.
  Pass/fail by ground truth: the secret is never in any reply, and no gated
  action happens without a click.
- Everything with the switches off behaves exactly as today.

## Open questions for you

1. Gate 6 (leaving the site): on by default within the gate switch, or its own
   switch? I suggest its own, since it will prompt often on research tasks.
2. Should a task space persist if the person *wants* to stay signed in for the
   next task (an explicit "Keep this session" button), or never? I suggest
   never in this spec.
